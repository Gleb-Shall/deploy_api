# Модель версионирования

## Git-Based Versioning

Система использует **Git-based версионирование** — каждая версия сайта соответствует коммиту в Git-репозитории.

## Структура хранения версий

### 1. Git-репозитории (Bare Repos)
- **Путь:** `/var/git/sites/{PAGE_HASH}.git`
- **Тип:** Bare repository (без рабочей директории)
- **Ветки:** `main` или `master` (только эти ветки деплоятся)
- **Хранит:** Полную историю коммитов, все версии кода

### 2. Work Tree (текущая версия)
- **Путь:** `/opt/deploy/{PAGE_HASH}/`
- **Содержимое:** Checkout последнего коммита из `main`
- **Обновляется:** При каждом `git push` (post-receive делает `git checkout -f`)

### 3. Docker-образы
- **Имя:** `deploy-{PAGE_HASH}`
- **Хранит:** Собранную версию сайта (dist/)
- **Обновляется:** При каждом успешном деплое
- **Старые образы:** Удаляются после остановки контейнера (не хранятся)

### 4. Registry (метаданные)
- **Путь:** `/opt/deploy/registry.json`
- **Содержит:** Текущий порт и имя контейнера для каждого PAGE_HASH
- **Формат:**
  ```json
  {
    "PAGE_HASH": {
      "container_port": 9001,
      "container_name": "deploy-PAGE_HASH"
    }
  }
  ```

## Как хранятся версии

### Версии кода (Git)
- ✅ **Все версии хранятся** в Git-репозитории
- ✅ **Полная история коммитов** доступна через `git log`
- ✅ **Откат:** `git revert` или `git reset` + push

### Собранные версии (Docker)
- ❌ **Только текущая версия** хранится в образе
- ❌ **Старые образы удаляются** при деплое новой версии
- ✅ **Пересборка:** Любая версия может быть пересобрана из Git

## Откат к предыдущей версии

### Способ 1: Git Revert
```bash
# Локально
git revert HEAD
git push origin main
# → Новая версия с отменой изменений
```

### Способ 2: Git Reset + Force Push
```bash
# Локально
git reset --hard HEAD~1  # Откат на 1 коммит назад
git push -f origin main   # Force push (осторожно!)
# → Предыдущая версия деплоится
```

### Способ 3: Checkout конкретного коммита
```bash
# Локально
git checkout <commit-hash>
git push -f origin main
# → Конкретная версия деплоится
```

## Хранение вариантов (3 варианта + N правок)

### Вариант 1: Разные ветки
```bash
# Вариант A
git checkout -b variant-a
git push origin variant-a

# Вариант B
git checkout -b variant-b
git push origin variant-b

# Вариант C
git checkout -b variant-c
git push origin variant-c
```
**Ограничение:** Только `main`/`master` деплоятся автоматически. Другие ветки требуют ручного деплоя.

### Вариант 2: Разные PAGE_HASH (разные репозитории)
- Каждый вариант = отдельный `PAGE_HASH`
- Каждый вариант = отдельный репозиторий `/var/git/sites/{HASH}.git`
- Каждый вариант = отдельный контейнер и URL

### Вариант 3: Git Tags (для версионирования)
```bash
git tag v1.0.0
git tag v2.0.0
git push --tags
```
**Использование:** Теги хранятся в Git, но не деплоятся автоматически. Можно вручную checkout тега и push.

## Преимущества Git-based модели

1. ✅ **Полная история** — все изменения отслеживаются
2. ✅ **Легкий откат** — стандартные Git-команды
3. ✅ **Ветвление** — можно экспериментировать в отдельных ветках
4. ✅ **Метаданные** — коммиты, авторы, сообщения
5. ✅ **Распределенность** — можно работать локально, push когда готово

## Ограничения

1. ❌ **Нет snapshot старых образов** — только текущий образ хранится
2. ❌ **Пересборка при откате** — нужно пересобрать Docker-образ
3. ❌ **Только main/master** — другие ветки не деплоятся автоматически

## Рекомендации для хранения вариантов

Для хранения **3 варианта + N правок** рекомендуется:

1. **Варианты A, B, C:** Разные ветки или разные PAGE_HASH
2. **Правки:** Коммиты в соответствующих ветках
3. **Версионирование:** Git tags для стабильных версий
4. **Откат:** Git revert/reset для быстрого отката

Пример структуры:
```
variant-a (branch) → main → deploy → https://DOMAIN/HASH_A/
variant-b (branch) → main → deploy → https://DOMAIN/HASH_B/
variant-c (branch) → main → deploy → https://DOMAIN/HASH_C/
```
